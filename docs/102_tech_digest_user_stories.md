# 技術ダイジェスト機能 ユーザーストーリー

技術に関する最新情報をバッチで収集し、同一内容の動画と記事を自動生成して pechka 上で閲覧できるようにする機能のユーザーストーリーである。技術的な裏付けと構成案は [407_tech_digest_pipeline.md](./407_tech_digest_pipeline.md) にある。

## 0. 前提

- pechka は個人利用のホームメディア基盤であり、認証・認可は存在しない（`docs/101`）。したがって登場人物は**「わたし」1 人**である。ただし振る舞う役割が 2 つあるため、ストーリー上は次のように書き分ける。
  - **視聴者としてのわたし** — 生成されたダイジェストを見る／読む
  - **運用者としてのわたし** — 生成の設定を変え、結果を確認し、誤りを直す
- 「ダイジェスト」= ある 1 日分の技術トピックのまとめ。1 つのダイジェストから**動画コンテンツ 1 件と記事コンテンツ 1 件**が生成され、両者は相互にリンクする。

---

## 1. エピック一覧

| ID | エピック | 狙い |
| :-- | :-- | :-- |
| E1 | 最新情報の自動収集と台本生成 | 情報を探しに行かなくても、その日のトピックが揃っている |
| E2 | 台本から動画を自動生成する | 手を動かさずに解説動画ができている |
| E3 | 同じ台本から記事を自動生成する | 同じ内容を読み物としても得られる |
| E4 | その日の気分で動画と記事を使い分ける | 状況に合った形式で消費できる |
| E5 | 生成物の品質を管理する | 誤りに気づき、直し、作り直せる |
| E6 | 日次で無人運転する | 毎朝、勝手に増えている |

## 2. E1: 最新情報の自動収集と台本生成

### US-1.1 情報源からの自動収集

> **運用者としてのわたし**は、登録しておいた技術情報ソースから記事候補が自動で集まってほしい。
> **なぜなら**、毎日自分で複数のサイトを巡回するのは続かないからである。

**受入条件**

- [ ] Hacker News（公式 API）、Zenn / Qiita、Publickey / InfoQ Japan、クラウド・OSS の公式ブログ（RSS）、GitHub Releases（公式 API）から候補を取得できる
- [ ] 情報源の一覧は設定として外出しされており、コード変更なしに追加・削除できる
- [ ] **HTML スクレイピングは行わず、RSS と公式 API のみを使う**（`docs/406` の判断基準を踏襲）
- [ ] 取得結果には必ず出典 URL・掲載元・タイトルが含まれる
- [ ] 同一 URL の記事は日をまたいでも重複して取り上げられない

### US-1.2 今日取り上げるトピックの選別

> **視聴者としてのわたし**は、集まった数十〜数百件から**本当に読む価値のある 3〜5 件**に絞られていてほしい。
> **なぜなら**、全部並べられても結局読まないからである。

**受入条件**

- [ ] LLM が候補を評価し、上位 3〜5 件を選ぶ
- [ ] 選別の観点（自分が使っている技術に近いか、一次情報か、実務に影響するか）がプロンプトとして明示され、調整できる
- [ ] 選ばれなかった候補も理由とともにログに残り、選別基準の妥当性を後から検証できる

### US-1.3 構造化された台本の生成

> **運用者としてのわたし**は、動画と記事の**両方の元になる 1 つの台本**が生成されてほしい。
> **なぜなら**、動画と記事で内容がずれると「同じ話を形式だけ変えて選ぶ」という体験が壊れるからである。

**受入条件**

- [ ] 台本は構造化 JSON で出力される（セクション、ナレーション文の配列、スライド定義、記事本文、出典）
- [ ] ナレーションは**文単位の配列**で出力される（音声・スライド・字幕のタイミングを揃えるため）
- [ ] 各セクションに出典が 1 件以上必ず含まれる
- [ ] 台本は DB に保存され、後段の工程だけを再実行できる
- [ ] LLM プロバイダをローカル（Ollama）と外部 API で切り替えられる

## 3. E2: 台本から動画を自動生成する

### US-2.1 ナレーション音声の合成

> **視聴者としてのわたし**は、聞いていて苦にならない日本語ナレーションで解説してほしい。

**受入条件**

- [ ] 台本のナレーション文ごとに音声が合成される
- [ ] 話者・話速を設定で変更できる
- [ ] 合成結果から各文の**実尺 (ms) が取得できる**
- [ ] TTS エンジンは常駐しており、実行のたびにモデルの再ダウンロードが発生しない

### US-2.2 スライド映像の生成

> **視聴者としてのわたし**は、話している内容がスライドとして目で追える動画であってほしい。
> **なぜなら**、技術の話は耳だけでは追いきれず、用語や箇条書きは見えている必要があるからである。

**受入条件**

- [ ] スライドは HTML/CSS のテンプレートとして定義され、レイアウト（タイトル、箇条書き、コード、比較表）を選べる
- [ ] **ナレーション 1 文につきスライドが 1 状態進む**（箇条書きが順に現れる、読んでいる項目がハイライトされる）
- [ ] 生成される映像に、動画生成 AI による映像は一切含まれない
- [ ] スライドのデザインを変えても、パイプラインの他工程に影響しない

### US-2.3 音声とスライドの同期

> **視聴者としてのわたし**は、ナレーションとスライドがずれていない動画を見たい。

**受入条件**

- [ ] スライドの切り替え時刻は**音声の実尺から自動的に決まる**
- [ ] 手作業でタイムラインを編集する工程が存在しない
- [ ] 同じ台本から生成し直せば、常に同じ尺の動画ができる（冪等）

### US-2.4 既存の配信基盤への載せ替え

> **視聴者としてのわたし**は、生成された動画を既存の Bluray 由来コンテンツと**まったく同じ操作感**で再生したい。

**受入条件**

- [ ] 生成動画は既存の ETL（ffmpeg ABR → HLS → MinIO → PostgreSQL）を通って登録される
- [ ] 画質バリアント切り替え・シークが既存コンテンツと同様に動作する
- [ ] サムネイルが自動で設定される（タイトルスライドを流用する）
- [ ] 一覧・検索の対象になる

### US-2.5 字幕

> **視聴者としてのわたし**は、音を出せない場所でも字幕で内容を追いたい。

**受入条件**

- [ ] 字幕は**台本と音声実尺から決定論的に生成**される（音声認識を経由しない）
- [ ] 既存の `subtitle_tracks` / `subtitle_cues` に格納され、既存のプレーヤーで表示される
- [ ] 既存の admin 字幕エディタでそのまま編集できる
- [ ] 人手で編集済み、または published のトラックを、再生成が黙って上書きしない

## 4. E3: 同じ台本から記事を自動生成する

### US-3.1 記事コンテンツの生成

> **視聴者としてのわたし**は、同じダイジェストを**読み物**としても得たい。
> **なぜなら**、コードや設定例は読んで手元にコピーしたいからである。

**受入条件**

- [ ] 同じ台本から Markdown 記事が生成される
- [ ] 記事は `content_type: article` のコンテンツとして登録される
- [ ] 記事本文は**ナレーションの書き起こしではない**。コード片・表・見出しを含み、読み物として成立している
- [ ] 各セクションに出典リンクが明示される

### US-3.2 記事の閲覧

> **視聴者としてのわたし**は、ブラウザ上で記事を快適に読みたい。

**受入条件**

- [ ] コンテンツ詳細画面で Markdown がレンダリングされて表示される
- [ ] コードブロックがシンタックスハイライトされ、コピーできる
- [ ] 出典リンクから元記事に飛べる

### US-3.3 記事の全文検索

> **視聴者としてのわたし**は、「あの話どのダイジェストだったか」を本文の言葉から探したい。

**受入条件**

- [ ] 記事本文が Elasticsearch にインデックスされる
- [ ] 既存の検索 UI から本文中の語で記事がヒットする

---

## 5. E4: その日の気分で動画と記事を使い分ける

### US-4.1 形式の切り替え

> **視聴者としてのわたし**は、開いたダイジェストを**その場で「動画で見る / 記事で読む」に切り替え**たい。
> **なぜなら**、通勤中は聞きたいし、机に向かっているときは読みたいからである。

**受入条件**

- [ ] コンテンツ詳細画面に、もう一方の形式へ切り替えるトグル／リンクがある
- [ ] 切り替え先が存在しない場合はトグルが表示されない
- [ ] 切り替えのために追加の API 問い合わせが発生しない（対応関係が非正規化されている）

### US-4.2 ダイジェストとしてのまとまり

> **視聴者としてのわたし**は、一覧で「同じ日のダイジェストの動画と記事」が別々の 2 件として散らばって見えるのを避けたい。

**受入条件**

- [ ] 一覧では 1 ダイジェスト = 1 カードとして表示される
- [ ] カードに、動画と記事のどちらが利用可能かが示される
- [ ] 日付順に並び、過去のダイジェストを遡れる

### US-4.3 途中まで見た動画の続き

> **視聴者としてのわたし**は、動画を途中でやめて、続きを記事で読みたいことがある。

**受入条件**

- [ ] 動画の再生位置に対応する記事のセクションへ移動できる

> 補足: `docs/101` では視聴履歴・レジューム再生は後フェーズ扱いである。このストーリーは優先度を下げ、E1〜E4 の基本形が動いてから着手する。

## 6. E5: 生成物の品質を管理する

### US-5.1 怪しい箇所への自動フラグ

> **運用者としてのわたし**は、LLM が自信を持てなかった箇所に**印がついていて**ほしい。
> **なぜなら**、全文を毎日読み直すつもりはないが、誤情報を放置もしたくないからである。

**受入条件**

- [ ] 生成時に低信頼と判定されたセクションに `flagged` が立つ
- [ ] admin 画面のダイジェスト一覧で flagged の有無が一目で分かる
- [ ] 人手で修正すると `flagged` が解除される（既存の字幕 cue と同じ挙動）

### US-5.2 内容の修正

> **運用者としてのわたし**は、誤りを見つけたら直したい。

**受入条件**

- [ ] admin 画面から台本・記事本文・字幕を編集できる
- [ ] 記事の編集は動画には影響しない（動画は再生成が必要である旨が示される）
- [ ] ダイジェスト単位で非公開にできる／削除できる

### US-5.3 工程単位の再実行

> **運用者としてのわたし**は、失敗した工程だけをやり直したい。
> **なぜなら**、TTS だけ失敗したのに収集からやり直すのは無駄だからである。

**受入条件**

- [ ] 台本が保存されており、台本以降の工程を単独で再実行できる
- [ ] 話者やスライドデザインを変えて動画だけ作り直せる
- [ ] 再実行は冪等であり、重複したコンテンツが生えない

### US-5.4 出典の追跡

> **運用者としてのわたし**は、記述の根拠になった元記事を常にたどれるようにしたい。

**受入条件**

- [ ] すべてのセクションに出典が保持され、動画（スライド上）・記事（本文中）の両方に表示される
- [ ] 元記事の本文全文が保存・再配布されていない

## 7. E6: 日次で無人運転する

### US-6.1 定期実行

> **視聴者としてのわたし**は、朝起きたら**その日のダイジェストができている**状態にしたい。

**受入条件**

- [ ] 日次のスケジュール実行として動作する（Argo CronWorkflow）
- [ ] 実行時刻と有効／無効を設定で変更できる
- [ ] 前日分が未完了でも、当日分の実行が阻害されない

### US-6.2 失敗時の可視化

> **運用者としてのわたし**は、生成が失敗したことに**気づける**ようにしたい。

**受入条件**

- [ ] 失敗したダイジェストは `error` 状態として記録され、admin 画面で確認できる
- [ ] どの工程で失敗したかがログから分かる
- [ ] 情報源が一時的に落ちていても、残りのソースで処理が継続する

### US-6.3 既存パイプラインへの非干渉

> **運用者としてのわたし**は、ダイジェスト生成が**既存の Bluray 取り込みを妨げない**ことを保証したい。

**受入条件**

- [ ] ダイジェスト生成は `etl-bluray` とは独立した WorkflowTemplate として定義される（`docs/406` の `subtitle-gen` と同じ方針）
- [ ] 長時間のトランスコードが競合してもどちらかが待たされるだけで、失敗しない

## 8. 優先順位と段階リリース

`docs/407` の D0〜D6 に対応する。

| 段階 | 含むストーリー | この段階で得られるもの |
| :-- | :-- | :-- |
| **MVP-1** | US-1.3（手書き台本）, US-2.1, US-2.2, US-2.3 | 手で書いた台本から動画 MP4 が焼ける。**方式が成立するかの検証** |
| **MVP-2** | US-2.4, US-2.5 | 生成動画が pechka で普通に再生できる |
| **MVP-3** | US-1.1, US-1.2, US-1.3 | 実ソースから台本が自動生成される |
| **MVP-4** | US-3.1, US-3.2, US-3.3 | 記事が生成され読める |
| **MVP-5** | US-4.1, US-4.2, US-6.1 | **動画と記事を気分で使い分けられ、毎朝勝手に増える**（当初要求の完成形） |
| 以降 | US-5.1〜US-5.4, US-6.2, US-6.3, US-4.3 | 運用に耐える品質管理 |

MVP-1 を最初に置いているのは、**このアイデアで一番不確実なのが「見るに耐える動画がコードだけで作れるか」だから**である。ここが成立しなければ収集も記事も無意味になるため、LLM も情報収集も入れずに手書き台本 1 本で先に確かめる。

## 9. 未決事項

ストーリーを確定させる前に判断が必要なもの（詳細は `docs/407` §4）。

1. **自動公開するか、人手レビューを挟むか** — US-5.1 の設計が変わる。推奨は「自動公開 + flagged による事後レビュー」
2. **LLM をローカル（Ollama）で完結させるか** — US-1.3 の品質基準に直結する。実装後に実測して判断する前提
3. **1 日 1 本か、トピック単位で複数本か** — 本ストーリー群は「1 日 1 本のダイジェスト」を前提に書いている。トピックごとに独立した短い動画にする案もあり、その場合 US-4.2 の一覧設計が変わる
